# Agent Note: 镜像内全局 ddc CLI

Status: implemented

## Problem

镜像已有 apktool 与 adb，但 apktool 只把 DEX 反汇编成 smali，没有从 DEX 回到可读 Java 的反编译器。用户要求内置 [ejfkdev/ddc](https://github.com/ejfkdev/ddc)（Android DEX → Java 反编译器）并让它像其他工具一样在 `PATH` 中直接可用。

## Decision

固定上游 release 原始二进制 `DDC_VERSION=0.1.28`，按架构分别固定发布资产 SHA-256（`DDC_SHA256_AMD64`、`DDC_SHA256_ARM64`）；用 `dpkg --print-architecture` 探测架构而不是 `TARGETARCH`，映射到上游资产名 `x86_64-unknown-linux-gnu` / `aarch64-unknown-linux-gnu`，把未校验的下载落在 `/tmp/ddc`，`sha256sum -c` 通过后才 `install -m 0755` 到 `/usr/local/bin/ddc`，并以 `test "$(ddc --version | head -n1 | awk '{print $1, $2}')" = "ddc $DDC_VERSION"` 在构建期断言版本。

"添加到 PATH" 不需要额外编排：`/usr/local/bin` 同时出现在镜像 `ENV PATH` 和 Debian `/etc/profile` 的 `PATH` 里，因此非登录 shell、登录 shell 与裸 `docker exec` 都直接命中同一个入口。这也是 ddc 与 apktool 的机制差异 —— apktool 是 JAR，必须有一个 `java -jar` 启动脚本；ddc 是单个静态链接 ELF，本身即入口，所以没有 wrapper、alias、符号链接或 `profile.d` 脚本。

构建期冒烟在 `bash -c` 与 `bash -lc` 两条路径都从 `/tmp` 调用 `ddc --version`，容器冒烟额外包含裸 `docker exec --workdir /tmp` 调用；两者都不在安装目录里执行，用来证明调用不依赖工作目录与 shell 类型。

## Alternatives considered

- `cargo install ddc-cli` 或按 README 从源码 `cargo build --release`：最强的理由是复用镜像已有的 Rust 1.98.1 工具链，不必信任上游预编译产物，且不依赖 GitHub release 是否可用。放弃的原因是构建要拉取整个 crates 依赖树并做 release 优化编译，构建时间和缓存体积都远超下载一个 4MB 二进制；同时会把工具链版本和产物绑死。
- `cargo binstall ddc-cli`：拿到的同样是上游预编译二进制，但多引入一个 cargo 子命令和它的配置面；直接用 `curl` 取官方 release 资产中间层更少。
- 从 Debian 仓库安装：Debian 没有这个包，第三方项目也进不了归档，不可行。
- 下载后不校验、直接落 `PATH`：少一次哈希计算，但破坏本镜像"固定版本 + SHA-256 校验"的既有约定（apktool、Frida、JDK 都遵守），也让上游资产被替换时无从发现。
- 额外加 wrapper 脚本或 `profile.d` 条目来满足"加到 PATH"的字面要求：不必要，`/usr/local/bin` 已在两条 PATH 路径中；多一层编排只增加故障面，还会掩盖真正的 PATH 不变量。
- 用 BuildKit 的 `TARGETARCH` 选资产：更贴近多架构构建语义，但本文件 JDK 段已经用 `dpkg` 探测，且注释明确要求在不开 BuildKit 时也不拿错架构；保持一致比多一种机制更重要。

## Testing

- 新增 [ddc 配置测试](../../../../tests/ddc.test.mjs)：断言版本 pin、两个架构的 digest 均为 64 位十六进制且互不相同、`dpkg` 探测与资产映射、下载 URL 模板、`/tmp` 中转与校验、`install` 目标、构建期版本断言写法；另有一条用上游真实 `--version` 横幅验证断言解析，以及一条断言构建期冒烟与容器冒烟都在安装目录之外调用 ddc。
- 本机端到端复现：把 Dockerfile 中 ddc 段的 `RUN` 原文抽出执行（唯一插桩是把 `install` 目标改到 `/tmp/ddc-verify/bin`），`curl` 换成走 `api.github.com` 资产端点的替身（本机 github.com 直连被出口拦截）。观察到的 URL 为 `https://github.com/ejfkdev/ddc/releases/download/v0.1.28/ddc-v0.1.28-x86_64-unknown-linux-gnu`，校验输出 `/tmp/ddc: OK`，`test 'ddc 0.1.28' = 'ddc 0.1.28'` 通过；把隔离目录放进 `PATH` 后 `ddc --version` 打印 `ddc 0.1.28 — DEX → Java decompiler`。该右值用 `file` 判定为静态链接 ELF，`ldd` 报 non-dynamic，不依赖发行版 glibc，所以 bookworm 上无需额外运行库。
- Node 回归 142 项：140 项通过、2 项非 root 测试跳过；`shellcheck` 与 `bash -n` 对改动的 `tests/image-smoke.sh` 通过。当前环境无 Docker CLI，完整镜像构建与容器冒烟未在本地执行。

## Consequences

调用方不需要知道 ddc 装在哪：任意目录、任意 shell（含登录 shell 与裸 `docker exec`）都能直接 `ddc`，且没有 wrapper 需要跟随升级。代价是新增两个架构的 digest 维护项，升级必须四处同步（`DDC_VERSION`、两个 SHA-256、README 版本号），漏一处会在构建期或测试期失败。下载依赖 GitHub release 可用性，与 apktool 同一风险面。引入的是第三方个人项目（非发行版渠道、非官方 Android 工具链）的预编译二进制，信任来自固定版本加 SHA-256 校验，而不是上游签名；非 macOS 构建经 UPX 压缩，某些安全策略或内存受限环境可能拦。本机是 amd64，arm64 资产无法在本地执行，其正确性只能由原生 ARM runner 的构建期断言覆盖，属于真实缺口。
